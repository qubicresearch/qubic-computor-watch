What we can and can't say: the collection-hub-to-exchange half of this chain (steps 1-3) is fully verified, current, and repeats reliably. We also directly checked whether an active computor sweeps its own earned revenue out to a hub while it still holds its seat — across 5,000 real transactions checked (5 long-tenured computors, seeded as far back as tick 17,983,428, 1,000 transactions each), we found zero such sweeps. ~93% of that volume is a zero-value housekeeping transaction (inputType 6, to the network's own null address) sent almost every tick — live confirmation that revenue accounting counts transaction presence, not verified work. The only real non-zero transfers found were Ant Colony bond postings (1,000,000 QU to that same null address, not a hub). The coherent read: there's no reason to sweep funds while an identity still holds its seat — the operator already controls the keys. Funds return to the hub only when a candidacy ends, via the same-tick stake-reclaim mechanism already confirmed earlier in this investigation (202 of 202 checked, same tick, same destination). So the full loop is: seed in, funds sit and accumulate for as long as the seat is held, reclaimed out in one lump sum on exit — not a continuous drip.

The mechanism, in brief

Every candidate identity is auto-funded by pool software (not manually by an operator) the moment it's first used — reproduced directly on independent hardware, four separate times, with zero operator involvement. Each real work submission posts a 1,000,000 QU bond that the network independently re-verifies and only refunds if the recomputed solution matches exactly. Winning a seat isn't a flat contest across all 676: the top 451 ranked identities are copied forward automatically each epoch, while the remaining 225 seats are recomputed after every single valid submission network-wide — a new identity only has to beat the current worst of that 225, not the whole network.
